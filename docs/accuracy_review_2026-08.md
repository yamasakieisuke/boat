## 結論（先に3行）

1. **予測力はある**。的中率28.7%はランダム購入（6.9点/120通り = 5.75%）の約5倍。
2. **買い目は価値を壊している**。回収率70.1%は3連単の払戻率75%を下回る。当てにいく力が、そのままオッズに織り込まれた人気どころに寄っている。
3. **そして今、これ以上の検証が積み上がらない状態になっている**。GitHub Actions移行（2026-05-15）以降、verify結果はどこにも永続化されていない。ここを直すのが最優先。

## 1. データ蓄積の現況 — ここが最大の問題

「結果が溜まっている」つもりだったが、実際には溜まっていない。

| データ | 実態 |
|---|---|
| `data/results_csv/` | ✅ 500日分。git管理、健在 |
| `data/logs/{date}/*_pred.json`（予測ログ） | ❌ ローカルは `20260517` の84件のみ（iCloud事故で消失）。Actions上では毎run破棄 |
| `data/logs/verify_history.json` | ❌ 存在しない。`data/*` が.gitignore対象、Actionsのrunnerと共に消える |
| `output/data/accuracy/*.json`（週次精度） | ❌ 存在しない |
| WP配布用ミラー `wordpress/.../accuracy/` | ⚠️ **2026-W17（4/20-26）の1件だけ**。Coworkでローカル実行していた最後の週 |
| `output/wordpress/*/*_payload.json` | ⚠️ 281件（58日分、3-5月）だけ生存。**今回の分析はこれが唯一の情報源** |

### 原因（3つ独立している）

1. **`verify.py --report weekly` がどのワークフローからも呼ばれていない。** grep済み。週次精度レポートはCowork時代の手動運用のまま止まっている。最後の生成は `2026-04-27T08:57:42`。
2. **`verify.yml` が commit するのは `data/players/ data/motors/ data/results_csv/` だけ。** verify本体の出力（`verify_history.json` / `output/data/verify/`）はrunner終了で消える。
3. **`predlogs-{DATE}` artifact の retention が14日。** 予測ログを事後に取り戻せる窓が2週間しかない。

つまり **日次verifyは毎日走っているが、その結果は毎日捨てられている**。WordPressに送られる `review_summary` だけが唯一サーバ側に残っているが、集計可能な形では手元に戻ってこない。

## 3. 診断

| 効いているもの | 効いていない／害になっているもの |
|---|---|
| スコアの順序付け（点数を削るほどROI改善） | 買い目の広げ方（本命以外の51%が足を引っ張る） |
| 1着予測（53.6%） | confidence の較正（80+が最悪、非単調） |

**根本の構図**: 予測は「当たる馬券」を探せているが「割に合う馬券」を探していない。verifyが的中率しか測っていないので、的中率を上げる改修が回収率を下げても検知できない構造になっている。

## 4. 改善計画

### P0 — 検証基盤の修復（これがないと以降が全部積み上がらない）

**P0-1. verify結果を永続化する**
- `.gitignore` に `!data/logs/verify_history.json` の例外を追加、`verify.yml` の commit 対象に含める
- `verify.yml` の週次（日曜）ステップとして `python3 scripts/verify.py --report weekly --no-refresh` を追加し、`wordpress/boat-forecast-viewer/data/accuracy/` を commit する
  → `deploy-wp.yml` が `wordpress/**` push で自動FTPSデプロイするので、WP側の精度ページも自動更新される（現在4月末で止まっている）
- ⚠️ `_update_accuracy_index()` は `ACCURACY_DIR` の glob で index.json を作り直す。Actions上は毎回空なので **今のまま週次を有効化すると index.json が1週分に潰れる**。`WP_ACCURACY_DIR` 側もマージ元に加える修正が先。

**P0-2. predlogs artifact の retention を 14 → 90日に**
- `predict.yml` の2箇所。事後検証の窓が2週間しかないのはリスク。コストはほぼゼロ

**P0-3. verify に回収率（ROI）を組み込む**
- `results_csv` に `won3_pay` / `won3_pop` / `trio_pay` / `won2_pay` が既にある。買い目タイプ別のROIと点数を `verify_history` / 週次レポートの一級指標にする
- 併せて**的中時の人気分布**も記録する（人気サイドへの寄りを検知するため）
- 実装の下敷きは `scripts/analyze_roi.py`（今回作成）

### P1 — 期待値の改善（P0完了後、2週間の蓄積を待って判断）

**P1-1. 展示/オッズ更新パイプラインの検証**（最優先の仮説）
- pred.json に**更新前の買い目も残す**ようにして、同一レースで更新前/後をA/B比較できる形にする
- 悪化が確認されたら、展示タイム・オッズの重みを下げるか、更新自体を止める
- 749R・-16ptは、他のどのチューニングよりインパクトが大きい

**P1-2. 買い目点数の削減**
- 「その他」（62.0%）と「穴」（65.5%）は本命（75.9%）より明確に悪い。廃止または大幅縮小を検討
- ただしブログ記事としての読み物性は落ちる。**表示は残してROI集計から分けるという選択肢もある**（後述の目的定義次第）

**P1-3. confidence の較正**
- 現状 conf は買い目点数の決定に使われているが、ROIとは逆相関。conf を「的中率の予測値」として実績で較正し直す
- 少なくとも conf 80+ で点数を増やす挙動は見直す

**P1-4. 券種の見直し**
- 本命→2連単で80.5%（的中35.1%）。3連単一本である必然性を再検討する価値がある

### P2 — 蓄積後に再判断

- **会場別の運用差**（宮島38.5% vs 桐生115.1%）。n=100前後では確定できないので、P0-1で蓄積が再開してから3ヶ月後に再測
- **TODO #3 series_score の D案**（`WEIGHTS["series_score"] = 0`）。判断材料の verify_history が消失したため、蓄積再開後に測り直し
- **TODO #2 EV閾値 1.30 の最適化**。ROI指標が入って初めて意味のあるチューニングになる

### 先に決めるべきこと（目的の定義）

3連単の払戻率は75%。**恒常的に回収率100%を超えるのは、この競技では相当に難しい**。5月時点で75%に到達しているのは既に健闘している水準。

- **目的が「収益」**なら → P1-2/P1-4 を強く進めて点数を絞り、ROI 100%超を狙う。記事のボリュームは犠牲になる
- **目的が「ブログの読み物・的中率」**なら → 現行のフル買い目でよく、ROIは参考指標に留める。ただしその場合でも P0（蓄積）は必須

この判断で P1 の優先順位が変わるので、先に決めたい。

## 追補（2026-08-12）— 点数の限界効用とイン偏重

ユーザー方針の確定: **実際の買い目として使う / 3連単にこだわる / 点数は削りたい**。
→ 2連単への振替（P1-4）は取り下げ。以下は3連単前提の分析。

明確な出血点: 穴1点目（2,315点・56.8%）／ その他2点目（798点・30.0%）／ 抑え4点目（79点・0%）。

### 削り方のシミュレーション

| 構成 | 点/R | 的中率 | 回収率 | 5月以降の回収率 |
|---|---:|---:|---:|---:|
| 現行フル | 7.3 | 30.2% | 70.1% | 75.0% |
| **死に筋除去**（その他2点目以降 / 抑え4点目 / 穴1点目を削除） | 6.2 | 27.8% | **72.6%** | **78.1%** |
| 本命4+抑え1-3点目 | 4.7 | 23.7% | 73.7% | 76.4% |
| 本命4点のみ | 3.6 | 17.3% | **75.9%** | **77.0%** |

**削るほどROIが上がる**という関係は5月以降のサブサンプルでも再現。「死に筋除去」が的中率の犠牲（-2.3pt）に対してROI改善（+2.5pt / 5月は+3.1pt）のバランスが最も良い。

### イン偏重の定量

| 艇番 | 本命の頭に選んだ率 | 実際の1着率 | 差 |
|---|---:|---:|---:|
| **1** | **88.1%** | **57.9%** | **+30.2pt** |
| 2 | 4.4% | 13.3% | -9.0pt |
| 3 | 3.9% | 11.7% | -7.8pt |
| 4 | 2.0% | 9.2% | -7.2pt |
| 5 | 1.0% | 5.1% | -4.2pt |

- 頭を1号艇にしたレースでの1着的中は **60.3%**。「常に1号艇」の基準値57.9%に対し **+2.4pt しか上乗せできていない**＝頭の選択は実質ノーシグナル
- **1号艇が勝たなかった1,328Rのうち、83.2%（1,105R）で頭を1号艇にしていた**。インが飛ぶ場面をほぼ全く先読みできていない
- 買い目全体の頭の広がりも狭い: 頭1種類 23.0% / 2種類 52.8% / 3種類以上 24.2%

### ただしモデルは「インが弱い」ことを知っている

`top_picks` の1号艇スコアと2番手スコアの差（gap）で層別すると、1号艇1着率がきれいに単調:

| gap 五分位 | R数 | 1号艇1着率 | 3連単的中率 | 回収率 |
|---|---:|---:|---:|---:|
| 最小（〜+0.054） | 556 | **46.4%** | 14.0% | 97.1% |
| 2 | 556 | 52.3% | 14.9% | 76.2% |
| 3 | 556 | 60.6% | 18.0% | 66.7% |
| 4 | 556 | 67.1% | 21.4% | 75.2% |
| 最大（+0.169〜） | 556 | **74.8%** | 23.9% | 75.7% |

**gap は1号艇の信頼度を46%〜75%の幅で正しく識別できている。にもかかわらず、どの帯でも頭は1号艇のまま**。使える情報を持っていて使っていない、というのが偏重の正体。

`is_rough` も方向は正しい（発動時の1号艇1着率42.2% / ROI 106.5%）が、頭=1号艇のレース2,780Rのうち **109R（3.9%）でしか発動していない**。閾値が保守的すぎる。

⚠️ ただし **gapで「買う/見送る」を決めてもROIはほぼ改善しない**（gap≥+0.030で74.9% vs 全体73.7%）。低gap帯は的中率が低い代わりに配当が高く、期待値としては打ち消し合っている。gapの正しい使い道は**見送りではなく「頭を散らす」判断**。

### 改訂した優先順位

1. **P1-2（点数削減）を最優先に格上げ** — 「死に筋除去」ルールの実装。実データで裏付けがあり、副作用が読める
2. **P1-5（新規・頭の散らし）** — gap下位帯で1号艇1着固定をやめ、2着候補を頭に立てた買い目を混ぜる。効果は既存データでは測れない（別の買い目を打つシミュレーションになるため）ので、**P0の蓄積基盤が直った後に実測でA/Bする**
3. `is_rough` の発動閾値を緩める（現行3.9%は少なすぎる）
4. ~~P1-4 券種の見直し~~ → 3連単で固定、取り下げ
5. tier内の並び順を「スコア順」から「実績ROI順」に変える検討（本命4点目・抑え3点目が良いという逆転現象への対応）
